# Design Doc: AI Agent Context Layer

**Date:** 2026-06-13
**Status:** Approved — ready for implementation
**Scope:** Connect Claude Code (in xterm.js terminal) to IDE state via MCP server
**Effort:** 3–5 days (~300–500 lines of new code)

---

## Problem

superGDS Studio has all the pieces for an "AI that knows what you're pointing at" experience, but they're not connected:

- The **viewer** (OpenLayers) tracks which polygons are selected and their provenance (file, line, function, call chain).
- The **iframeBridge** stores `currentComponents` on every selection event — rich data that nothing consumes.
- The **Monaco editor** knows which file is open and where the cursor is.
- **Claude Code** runs in the xterm.js terminal but has zero visibility into any of this.

The result: the user clicks a polygon, sees its provenance in the source panel, but when they ask Claude Code about it, Claude has no idea what they're talking about. The UX feels disconnected.

Meanwhile, **GDSFactory+** already ships `gfp-mcp` — an MCP server that connects Claude Code to their VS Code extension. They can build cells, explore PDKs, and run DRC through AI. But they lack our provenance-first reverse lookup (polygon → source code line). This is our differentiation.

---

## Design

### Architecture

```
┌─────────────┐   postMessage    ┌──────────────────┐   HTTP/WS    ┌──────────────────┐
│  Viewer      │◄───────────────►│  Express Server   │◄────────────►│ Claude Code       │
│  (iframe)    │  selectComponents│  + /api/ide-state │   MCP stdio  │ (xterm.js PTY)    │
│              │  highlightPolygons│                  │              │                   │
└─────────────┘                   └────────┬─────────┘              └───────────────────┘
                                           │
                                  ┌────────▼─────────┐
                                  │  supergds-mcp      │
                                  │  (MCP server)      │
                                  │  reads /api/ide-state│
                                  └───────────────────┘
```

The MCP server is a thin Node.js process that:
1. Exposes tools to Claude Code via the MCP protocol (stdio transport).
2. Reads IDE state from the Express server's `/api/ide-state` endpoint.
3. Sends commands back to the Express server to trigger actions (run script, highlight source).

### MCP Tools

| Tool | Parameters | What it does |
|------|-----------|--------------|
| `get_selected_components` | — | Returns `currentComponents` array with full provenance (provId, layer, bbox, file, line, function, call_chain) |
| `get_open_file` | — | Returns the currently open file path and cursor position in Monaco |
| `get_build_status` | — | Returns last run output, exit code, generated GDS path, errors |
| `run_script` | `path: string` | Triggers a Python script run via `/api/run` with `GDS_PROVENANCE=1` |
| `highlight_source` | `file: string, line: number` | Highlights a code line in Monaco (calls `forwardToEditor`) |
| `select_by_source` | `file: string, line: number` | Selects corresponding polygons in the viewer (calls `sendSelectBySource`) |

### Data Flow

#### User clicks polygon → Claude gets context

1. User clicks a polygon in the OpenLayers viewer.
2. Viewer calls `postSelectedComponents()` (viewer.html:517), posting `selectComponents` message to parent.
3. `iframeBridge.ts` receives it, stores in `this.currentComponents` (line 57).
4. **NEW:** iframeBridge also POSTs to `/api/ide-state` with `{ type: "selection", components }`.
5. Express server stores this in an in-memory state object.
6. When Claude Code calls `get_selected_components`, the MCP server fetches from `/api/ide-state`.
7. Claude returns structured provenance to the user: "You selected an electrode on layer WG, generated by `create_electrode()` at line 342, iteration 3 of the loop."

#### User asks Claude to modify → Claude changes code and rebuilds

1. User says "make the electrode spacing 2µm wider."
2. Claude calls `get_selected_components` → sees the electrode came from `ELECTRODE_CONFIGS[2]` in `suspended_superconductor_standalone.py:342`.
3. Claude edits the file, changing the spacing parameter.
4. Claude calls `run_script("suspended_superconductor_standalone.py")`.
5. Express server runs the script with `GDS_PROVENANCE=1`, generates new GDS + provenance.
6. Express server pushes the updated GDS to the viewer via WebSocket (existing `handleRun` flow in studio.ts:695).
7. Claude calls `highlight_source(file, line)` to show which line it changed.
8. Claude calls `select_by_source(file, line)` to highlight the modified polygons in the viewer.

## Implementation Plan

### Step 1: Add `/api/ide-state` endpoint to Express server

**File:** `server/stateRoutes.ts` (new)

```typescript
// In-memory IDE state — shared between Express and MCP server
interface IdeState {
  selectedComponents: ComponentSelection[];
  openFile: string | null;
  cursorPosition: { line: number; column: number } | null;
  buildStatus: {
    lastOutput: string;
    exitCode: number | null;
    gdsPath: string | null;
    errors: string[];
  } | null;
}
```

- `GET /api/ide-state` — returns current state (for MCP server to poll).
- `POST /api/ide-state` — updates state (from iframeBridge, Monaco events).
- `POST /api/ide-state/command` — sends commands (run script, highlight, select).
- Wire into existing Express app in `server/index.ts`.

**Effort:** ~80 lines, ~1 hour.

### Step 2: Wire iframeBridge to POST selection state

**File:** `frontend/iframeBridge.ts`

In the `selectComponents` case (line 55–58), after storing `this.currentComponents`, POST to `/api/ide-state`:

```typescript
case 'selectComponents': {
  const components = msg.components || [];
  this.currentComponents = components;
  // NEW: push selection to server state
  fetch('/api/ide-state', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ type: 'selection', components }),
  }).catch(() => {});
  // Forward to editor (existing behavior)
  this.forwardToEditor(components);
  break;
}
```

Also wire Monaco cursor position changes — listen to `onDidChangeCursorPosition` and POST to `/api/ide-state`.

**Effort:** ~30 lines, ~30 min.

### Step 3: Wire studio.ts to POST build status and open file

**File:** `frontend/studio.ts`

In `handleRun()` (line 695), after the EventSource completes, POST the build result to `/api/ide-state`:

```typescript

  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({

```

In `openFile()`, POST the current file path.

**Effort:** ~30 lines, ~30 min.

### Step 4: Build `supergds-mcp` MCP server

**File:** `mcp/supergds-mcp.ts` (new)

A lightweight MCP server using `@modelcontextprotocol/sdk`:

```typescript
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';

const server = new McpServer({ name: 'supergds', version: '0.1.0' });

const IDE_STATE_URL = process.env.SUPERGDS_STATE_URL || 'http://localhost:3000/api/ide-state';

async function getIdeState() {
  const res = await fetch(IDE_STATE_URL);
  return res.json();
}

server.tool('get_selected_components', 'Get currently selected GDS components with provenance',
  {}, // no params
  async () => {
    const state = await getIdeState();
    return { content: [{ type: 'text', text: JSON.stringify(state.selectedComponents, null, 2) }] };
  }
);

server.tool('get_open_file', 'Get the file currently open in the Monaco editor',
  {},
  async () => {
    const state = await getIdeState();
    return { content: [{ type: 'text', text: JSON.stringify({ file: state.openFile, cursor: state.cursorPosition }) }] };
  }
);

// ... get_build_status, run_script, highlight_source, select_by_source
```

**Key details:**
- Transport: stdio (Claude Code launches it as a child process).
- State source: polls `GET /api/ide-state` from Express server.
- Commands: `run_script` calls `POST /api/run`, `highlight_source` calls `POST /api/ide-state/command`.
- No persistence needed — state is ephemeral, lives in Express server memory.

**Effort:** ~200 lines, ~2 hours.

### Step 6: Server-side askClaude relay

**File:** `server/stateRoutes.ts` (extend from Step 1)

The `/api/ide-state/command` endpoint for `askClaude` type:
- Stores the question + components in IDE state.
- Injects a specially formatted line into the xterm.js PTY's stdin.

This is the trickiest part. Two approaches:

**Option A (simpler):** Write the question to a file (`/.superGDS/pending-question.json`) and add to `CLAUDE.md`: "Check `.superGDS/pending-question.json` when the user seems to be asking about the layout." Claude Code reads it on next prompt.

**Option B (ideal):** Use the terminal's PTY to inject a newline that Claude Code sees as part of the conversation. This requires the WebSocket terminal connection in `server/terminalRoutes.ts` to support server-initiated output injection.

Recommend **Option A** for now — it works with zero terminal hacks and Claude Code's file-reading is reliable.

**Effort:** ~30 lines, ~30 min.

### Step 7: Configuration and CLAUDE.md updates

Add to project `CLAUDE.md`:

```markdown
## AI Agent (superGDS MCP)

When the user asks about the GDS layout, a selected component, or what they're looking at:
1. Call `get_selected_components` to get provenance data (file, line, function, call chain).
2. Call `get_open_file` to see what code they're editing.
3. Use provenance to understand which code generated the component they're asking about.

When modifying a layout:
1. Use provenance from `get_selected_components` to find the exact code location.
2. Edit the Python script at that location.
3. Call `run_script` to rebuild with provenance tracking.
4. Call `select_by_source` to highlight the modified polygons.
```

Add to `package.json`:
```json
{
  "scripts": {
    "mcp": "npx tsx mcp/supergds-mcp.ts"
  }
}
```

User configures Claude Code:
```bash
claude mcp add supergds -- npx tsx mcp/supergds-mcp.ts
```

**Effort:** ~20 lines, ~15 min.

## What This Unlocks

### Immediate (this PR)
- Click polygon → ask Claude about it → Claude knows exactly which code, which function, which loop iteration generated it.
- Ask Claude to modify → it edits the right line → rebuilds → shows result.
- The `askClaude` UI in the viewer (the text input + send button at viewer.html:1829) works end-to-end.
- The `claude-mode` dropdown (Auto/Clipboard/Off) has a real "Auto" mode.

### Future (no code changes needed in MCP server)
- **Auto-rebuild**: Watch for file saves from Claude Code, auto-trigger `/api/run`.
- **Chat panel**: Add an embedded chat panel in the studio UI that calls the same MCP tools.
- **Bidirectional polygon highlighting**: Claude Code calls `select_by_source` → polygons flash in viewer.
- **Session persistence**: MCP server maintains state across Claude Code restarts.

## What We're Not Building (Deferred)

| Feature | Why |
|---------|-----|
| Draw → code generation | Separate problem, complex (viewer shapes → gdsfactory API calls) |
| Visual parameter editor | Python scripts are the source of truth, AI modification is better UX |
| WebGL rendering | Current GeoJSON rendering works for typical gdsfactory output (P3 in TODOS.md) |
| Embedded chat panel in studio | Claude Code in terminal is sufficient, chat panel is a polish item |
| Multi-user collaboration | Research/lab tool, single user |

---

## Risks

| Risk | Mitigation |
|------|-----------|
| MCP server can't reach Express server (CORS, port) | Same-origin by default; MCP server is localhost, Express is localhost |
| State polling latency (MCP polls `/api/ide-state`) | Acceptable for human-speed interactions (~100ms); could upgrade to WebSocket later |
| Claude Code doesn't call the right tool | CLAUDE.md instructions guide tool usage; provenance data is self-describing |
| Terminal injection for askClaude is fragile | File-based relay (Option A) avoids PTY hacks entirely |
| GDSFactory+ adds provenance tracking | Our fork's per-shape provenance is custom; even if they add it, we're first-mover in web IDE |
